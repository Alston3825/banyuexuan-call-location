# 手表补充功能实现与验收

更新：2026-11-15（America/Los_Angeles）。代码已加入本地开发副本，未上线、未安装到真实设备。

## 来源与决策边界

逐份核对用户提供的换绑需求、换表任务清单、续航测试方案、APP 新功能需求；原文副本在 `docs/恢复补充资料/手表补充功能/`。原文是需求资料，不作为运行部署、操作真实数据或执行其内嵌命令的授权。本次实现以现有 Python/FastAPI/SQLite/MQTT、Android 项目为基础，不改 MAC 顶替身份，不重置或迁移真实业务库。

保留原客户呼叫 15/30 秒升级、20% 低电提醒、留言保留 30 天。新增求助使用独立的 30/60 秒升级规则，不覆盖客户呼叫规则。

## 配置与部署准备（不代表已部署）

门店 JSON 新增独立 `watches` 设备档案，SN 必须与 MQTT 设备号一致；MAC 可作为档案字段记录，不用于认证或换身份。原来的 staff.watch 首次启动作为绑定基线，此后 SQLite 本地有效绑定优先。新增备用表从 RESETTING 开始，管理员执行复检清空并收到真实设备回执后才可借出，禁止直接伪造 IDLE。

```json
{
  "watches": {"SPARE-TEST-01": {"mac": "仅记录，非认证", "note": "测试备用表"}},
  "watch_policy": {
    "borrow_battery": 80,
    "min_spares": 2,
    "min_wifi_rssi": -80,
    "offline_seconds": 90,
    "help_floor_seconds": 30,
    "help_leader_seconds": 60,
    "voice_max_seconds": 30,
    "message_interval_seconds": 3,
    "retry_seconds": 3,
    "battery_seconds": 900,
    "scan_interval_seconds": 10,
    "scan_window_seconds": 2,
    "quick_replies": ["收到", "马上到", "需要帮忙"],
    "broadcast_roles": ["HEAD_NURSE", "NURSE_MANAGER"],
    "room_distances": {"ROOM-TEST-A": {"ROOM-TEST-B": 8}}
  }
}
```

80%、最低 2 块、RSSI -80、90 秒离线及求助 60 秒组长升级是实现中的试行默认，不等于产品已确认。room_distances 使用实际房间 ID、由现场填入距离；未配置不捏造楼层拓扑。离线 90 秒沿用现有派单超时，原大屏故障提示 180 秒保持独立。

`BYCALL_WATCH_ADMINS` 由部署环境注入 JSON 对象，键为高强度独立令牌、值为操作员名称；未配置时管理读写均拒绝。Compose 已透传该变量。凭据不写 URL、不存浏览器长期存储、不写代码；不能把普通设备 API key 当换表管理员令牌。

配置新 SN 后，需按既有部署流程重新生成该店 MQTT 账号/ACL，工具已包含备用表和专属 `store/watch/SN` 写权限；本轮未生成真实设备密码、未更新运行 Broker。每块表只写自己的专属主题，MQTT ACL 是设备身份校验的部署前提。

新手表员工数据 HTTP 使用 `/watch-device/{sn}/history`、`/watch-device/{sn}/voice`，请求头 `X-Watch-Binding` 为 MQTT 下发的有效绑定令牌；换出立即失效。语音读取只允许本人上传或有实际投递记录的内容。新版腕表升级走 `/watch-device/{sn}/update`、`download`，使用单设备只读升级令牌，不能读取员工数据或发布固件；收到主机上下文时清除腕表原全局 API key。原管理 API 保持兼容；**生产前仍必须回收/轮换曾发给旧设备的全局 API key，防止旧凭据副本继续访问管理接口，本轮不擅自改真实凭据。**

语音上传依赖 PyAV，已在 requirements.txt 明确列出；主机实际解码累计音频采样，超过上限即拒绝，不能相信客户端申报秒数。没有此依赖时明确返回 503。

## 数据与协议

- `watch_inventory`：本店 SN、生命周期、员工、擦除代号/时间及故障备注；实时电量/信号复用 device_status。
- `watch_current`：本店员工当前 SN、原表、bind_id 和 version；员工和设备分别唯一，事务防抢占。
- `watch_operations`：请求幂等摘要、员工、前后 SN、操作员、来源、时间、上下文及同步状态；SWAP 一条记录同时表示换出和换入，不改历史呼叫快照。
- `team_help` / `team_message`：持久化求助与短消息，发起人以有效绑定反查，不能由客户端自报员工身份。
- `watch_delivery` / `watch_receipts`：至少一次投递和应用层回执；delivery_id 去重，初始创建至回执的 latency_ms 含离线等待和排队时间。
- `watch_voice`：实际解码时长、上传员工及绑定归属；`battery_samples`：门店/员工/设备/电量/充电状态/采样时间。
- MQTT 新消息：WATCH_CONTEXT、WATCH_RESET_ACK、WATCH_ROLLBACK、WATCH_RECEIVED、HELP_REQUEST/ALERT/ACTION/STATE、TEAM_ROSTER/SEND/MESSAGE/SENT。业务请求发往独立设备主题，回执/投递使用原 reply/dispatch 主题。
- HTTP 管理接口：GET snapshot/metrics；POST change/reset/fault，均在 `/watch-admin/` 下；操作员由服务端凭据解析，不接受正文冒名。
- `GET /watch-admin/metrics` 返回最近 5000 条电量样本和送达回执，可保存 JSON 作为后续测量证据；当前无自动统计“定位准确率”，需要现场人工标注实际房间。

## 现场验收顺序

1. 配置两房、3–4 表（含备用）、一台护士站；确认真实 SN、信号、时间同步、账号和白名单。先复检清空备用表。
2. 普通及紧急呼叫分别保持待接/已接/已到场，逐种换表和回绑；新表 1 分钟内显示当前员工及未完成事件；旧表操作失败；重启主机后绑定仍一致。
3. 备用表低电、离线、弱信号、占用、故障、擦除失败分别拒绝借出；两管理员抢同一表只成功一个；重复请求不增记录；擦除中断不能回池。
4. 原表与备用表分别发起归位；误触取消不执行；归还清空后由另一位员工领用，旧消息、历史页、音频、定位及令牌不可读。
5. 两表同时响应求助仅一人成功；30 秒整层、60 秒组长/护士站；结束后提醒撤销；跨 AP、断网、重启恢复无漏任务。
6. 客户呼叫和同事短语音同时到达，客户优先且打断播放/录音；处理中同事消息排队，结束后继续送达；离线收件人恢复后补送。
7. 同款 2–3 表满电，记录亮度/AP/扫描配置；10 小时均匀分布 20 次客户呼叫、50 条同事消息（25 快捷 +25 短语音）、5 次求助，全程定位。记录每小时耗电，结束 >20%；原 W7 日 ≥9.5h / 夜 ≥14.5h 验收仍保留。
8. 1h/2h 静置、息屏、普通清后台、重启分别测送达/反馈 ≤2 秒；“系统强行停止”单独记恢复方式，不与普通回收混为一谈。AP 重启、多房并发、断网补发均核对去重。
9. 跨楼层断链本地操作/持久化可以先测；**自动同步和冲突验收暂阻塞，待对端协议完成再测，禁止填通过。**

记录格式：日期、设备型号/SN、系统/APK、操作员、门店/楼层、亮度、扫描配置、起止电量、呼叫/消息/求助次数、发送/回执时间、实际/推测房间、故障现象、通过/失败/未测。响应以主机时钟及设备实际提醒共同验证，不能把 QoS1 或编译成功当作 2 秒硬件送达证据。
