# 内部管理系统接口与数据契约草案

日期：2026-10-26。以下为拟定契约，尚未部署 HTTP API。管理系统源码、模型与认证方式未阅读，最终语言和路径可以调整，事件语义须保留。

## 数据归属

管理系统主责：门店、经营房间、员工、入住、护理关系、排班及满意度。呼叫本地节点主责：设备和当前绑定、呼叫任务、送达、接单、通话状态、到场确认、转交、完成与审计事件。两边以稳定 ID 对应，房号是展示名，不作为全局唯一 ID。

本地缓存当班需要的最小主数据与有效期；外网断开仍可按最后有效排班派单。快照过期、排班缺失或冲突时护士站显式提示并允许有审计的本地临时代班。恢复后协调临时覆盖，不能被旧版本覆盖。入住信息仅同步必要 ID/房间/责任关系，首期不需要健康档案。

## 拟定端点

| 路径与方法 | 用途 | 主要约束 |
|---|---|---|
| POST /integration/v1/master-data | 管理系统同步房间/员工/入住/班次/护理关系 | store_id、批次号、源版本、有效起止时间、删除标记；原子发布完整版本 |
| POST /device/v1/call-events | 设备或适配器上报按键 | 身份绑定店/房间；event_id + device_id 去重，重用 ID 不同正文返回冲突 |
| POST /calls/{id}/claim | 人员接单 | 服务端校验当班/候选/当前绑定；事务比较更新，仅一人成功 |
| POST /calls/{id}/arrive | 确认到场 | 当前负责人或明确授权；method 为 manual/nfc 等，BLE 推测分字段 |
| POST /calls/{id}/transfer | 显式转交 | 指定接收人、原因、期望版本，保留原责任历史；接收确认后切换 |
| POST /calls/{id}/complete | 完成 | 现场完成须已确认到场；远程解决可以跳过到场；原因及版本必填 |
| POST /device/v1/observations | BLE 观测 | watch_id、binding_id、beacon_id、RSSI、observed_at、序号；限批量与频率 |
| POST /device/v1/heartbeat | 设备状态 | 电量/固件/最后序号；服务端超时判定，未知与离线分开 |
| GET /integration/v1/events?after=cursor | 管理系统拉取业务事件 | 分店游标；按序分页；重复事件由接收端去重 |

所有写操作需要认证授权、请求 ID 和操作幂等键。设备请求中的房间和员工不能直接信任，要由凭证和当前绑定反查。跨店访问默认拒绝；护士站管理权限与普通护理师权限分开。仅原型内核目前实现建单、接单、到场、完成及转交规则，不等于上述端点已实现。

## 事件信封示例

```json
{
  "schema_version": "1.0",
  "event_id": "UUID",
  "store_id": "gaoxin",
  "aggregate_type": "call",
  "aggregate_id": "UUID",
  "aggregate_version": 3,
  "event_type": "call.arrived",
  "occurred_at": "2026-10-26T09:05:00+08:00",
  "received_at": "2026-10-26T09:05:01+08:00",
  "actor_id": "staff-test-01",
  "source_device_id": "watch-test-01",
  "binding_id": "binding-uuid",
  "correlation_id": "call-uuid",
  "payload": {"method": "manual"}
}
```

业务事件与任务更新在同一数据库事务写入 outbox。同步进程采用至少一次投递，接收方以 event_id 去重，成功确认后才标记已送达；失败指数退避并有人工可见的积压/死信。不能宣称网络天然恰好一次。接口认证与 TLS、密钥管理待具体部署定稿；不使用 MAC 当密钥。

乱序按 aggregate_version 缓存/补取，版本缺口触发对账。客户端时间只作观测，服务端接收时间用于审计；时钟偏差显式记录。各时间存有时区的时间戳，展示使用 Asia/Shanghai，班次区间为左闭右开，跨午夜夜班按业务日期区分。

## 状态与并行语音

主状态：pending → claimed → arrived → completed。claimed 可通过 remote 结案；取消为单独有权限状态，不能覆盖已完成历史。转交记录提出/接收两个动作；未接收前原负责人保留，已到场任务转交后重新等待新负责人到场。

语音有独立状态 idle/ringing/connected/ended/failed；与任务状态并行。接单不代表通话连通，通话结束不代表服务完成。提醒也独立记录目标、派发、设备确认和撤销；网络重发不能重复震动或重复建任务。

定位观测与推测区域独立保存；到场确认记录来源、操作人和时间。后续换房、交班、人员/设备解绑不能改写旧任务的入住、责任、班次及设备绑定快照。

## 阅读现有管理系统所需最小资料

源码根目录或技术栈说明、数据库与部署位置、房间/员工/入住/排班的脱敏结构、现有账号权限方式。无需真实客户数据、密码、生产密钥。确定后先做测试环境单向主数据同步与业务事件回传，再增加双向派单管理。

## 2026-11-10 已按《集成规范-呼叫定位系统》对齐(host/bycall/integration)
- ID:门店、房间、员工、入住全部用管理系统的 cuid 原值,呼叫系统不另造;房号、工号只用于显示。楼层是标签(如 `2F`、`B1`),不是数字。
- 呼叫按钮统一用 `service_code`(NEED_NURSE、BABY_CRY、MILK_STORAGE、HOT_WATER、CLEANING、EMERGENCY、CUSTOM);`EMERGENCY` 视为紧急。平板发来的编码不在服务项字典里会被拒绝。
- 主数据:主机每 30 秒增量拉取 stores/rooms/staff/stays/service-codes(`updatedSince` + `nextSince` 翻页),每 6 小时全量一次以发现删除;服务项每次全量。管理系统不通时用上次缓存启动。
- 分派:管理系统没有“每间房的责任护士”,所以改为“房间所在楼层 → 该楼层当前 `ON_DUTY` 且有手表的护士”;组长取角色在 `HEAD_NURSE / NURSE_LEADER / NURSE_MANAGER` 里的人(角色名是假设,待确认)。非在岗人员不参与分派。
- 信标:房内信标来自 `beacon_ids`;走廊、护士站信标管理系统没有,仍在主机本地配置。
- 写回:`POST /integration/v1/call-events`,按 call_id 幂等,每次发完整记录,断网自动重试。状态词除 `COMPLETED` 外(`PENDING/ACCEPTED/ARRIVED/CANCELLED`)是我们的假设。
- 待管理系统确认:① 列表翻页若多条记录 `updated_at` 相同,需要有次级排序,否则会漏记录(客户端已加防死循环);② 状态词表;③ 组长角色名;④ 没有当前入住时 `stay_id` 能否为空;⑤ 门店隔离的 API Key 是否对 `service-codes` 也生效;⑥ 手表登录是否需要 `auth/verify`(目前手表绑定走员工档案,没用到)。
- 未做:拉取 `/events` 实时触发同步(现为定时拉取)、`auth/verify` 的使用场景。

## 2026-11-13 分页异常保护

主数据 nextSince 与事件 nextSeq 在 hasMore=true 时不得重复已使用的游标；事件下一游标缺失也报 MgmtError，停止本轮拉取，避免停滞或循环请求。最终页 hasMore=false 可正常结束。已用模拟接口覆盖正常分页及异常游标，未连接真实管理系统。此保护不解决相同更新时间戳的次级排序问题；/events 仍未接入定时同步触发流程。

## 2026-11-15 手表补充接口

本地主机新增 `/watch-admin` 管理页面及 snapshot/metrics/change/reset/fault API，管理员令牌独立，不接受设备 API key 替代；绑定变更以员工和期望版本为依据、请求 ID 幂等，事务写入 watch_current/watch_inventory/watch_operations。管理系统旧 watch_id 不覆盖有效本地换绑。历史呼叫/定位归属和快照不改写。

腕表员工数据走 `/watch-device/{sn}/history`、`voice`，以有效绑定令牌校验；硬件只读升级使用独立设备令牌。新增 MQTT 业务请求走 `{store}/watch/{sn}`，设备 ACL 限制只能写自己的主题。回执/重试采用至少一次投递，非天然恰好一次。跨楼层出站传输与冲突契约尚缺，操作记录当前为 LOCAL_PENDING，没有 SYNCED 承诺。完整字段、默认值与待确认项见 docs/11。
